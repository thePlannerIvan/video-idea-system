# 内容契约与粗糙样张：这一屏画面上必须出现什么

## 核心边界

本阶段规定三件事：画面必须呈现什么信息（内容契约）、**上屏文字与花字是什么**（声明，见下）、以及这一屏大概是什么样（样张）。它**不决定最终构图、版面、字形取值和动效**。

接下来的两段各管一段：**静态画面**由做画面那一步在**录制之前**按 `visual-plan.json` 产出（拿走 SVG，不做 PPTX）；**时间、剪辑、花字落地、语义字幕与合成**归 `video-craft`。先按[表现能力咨询](表现能力咨询.md)了解可行能力，避免上游只因为手上已有截图就把概念限定成翻页。

## 一 Beat 一屏

每屏只回答一个问题：**这段口播期间，画面上必须出现什么？**

- 直接写画面上要出现的具体文字、元素、标签和数字；
- 对理论模型只写必须表达的语义事实，例如“人知道、AI 不知道的经验”，不要指定圆、箭头、矩阵或其他图形；
- 不要写“观众应理解什么”“解决动作”“画面关系”“边界”这类框架说明。若确有证据边界，把它写成画面上的明确标签或限制句；
- **一屏不得声明多个状态。** 如果一段口播要观众先看 A 再理解 B，先拆成两个 Beat，再各自配屏。状态属于下游的时间分组；**着重动画是录后按实测音频加的，不是契约状态**——不要因为它把「多状态」加回来；
- 不指定构图方案、动效、秒数。

## 内容契约字段

| 字段 | 必填 | 说明 |
|---|---|---|
| `screen_id` | 是 | 全局唯一，由 Beat ID 派生 |
| `beat_id` | 是 | 绑定的 Speech Beat，一 Beat 一屏 |
| `title` | 是 | 本段内容标题 |
| `question` | 是 | 本段口播要回答的问题 |
| `must_show` | 是 | **画面上必须出现的内容清单**。允许空数组：没有任何上屏文字的屏合法 |
| `must_express` | 否 | 必须看见的语义事实、差异或结论 |
| `exact_labels` | 否 | 必须原样出现的文字、数字或术语 |
| `evidence` | 否 | 数据或资料来源 |
| `sample` | 否 | 这一屏的粗糙样张。有画面的屏必须给 |

禁止加入本契约已退役的框架字段（`viewer_should_understand`、`information_to_show`、`information_surplus`、`evidence_refs`、`information_not_to_lose`、`known_assets`）。屏级也不承载任何画面设计或时间决定：图形形式、版面、状态、动效、配色、字体、秒数都不是内容契约的字段；那些名字归 `video-craft` 的分组步骤所有，本文件不复述那份名单。

**每一屏都必须在审阅页上显示出点什么**：`must_show`、`sample.assets[]`、`sample.captions[]` 三者至少有一个非空。三者都空是内容缺陷，不是「暂时没想好」。

## 上屏文字与花字归这里声明

- `must_show` 里以「文字：」开头的条目、`exact_labels`、以及 `sample.captions[]`，合起来就是**上屏文字与花字的唯一声明**。
- `sample.captions[]` 是花字层：按出场顺序，最后一条按重点句呈现；每一条绑定它要强调的那一句口播。
- 做画面那一步照声明把字画上去，不判断它们该不该存在；`video-craft` 的字闸门**读这一份声明**做检查，不另建 `on_screen_text.json` 之类的第二份声明。

## 样张：让用户看见，而不是读清单

条目文字审不出画面问题。用户读“必须出现 / 必须表达”的清单时，无法判断这一屏成立不成立；把真素材直接摆上去，一次就能看出素材摆错、缺页、数字对不上。

样张的四条纪律：

1. **只用真素材**：磁盘上已有的截图、页面渲染、联系表、原始数据行、报告实物、归档图集、录屏。**标注过的概念样张不算样张**——不要用示意图补位；
2. **只做静态摆放**：一屏一张 16:9 画面，花字层压在下沿；
3. **不做动效、不排字体配色、不追求精致**——动效和设计是后面的事；
4. **素材不够就露出缺口**，如实标出来。

样张仍然是内容层的：它让契约里漏掉的必见项显形。**样张漏掉的东西，就是契约缺陷**，要回契约补，而不是“反正后面会设计”。

## 简单设计在念稿审阅页上定

样张就是念稿审阅页的右半。**两种形状的片都要过这一页**，页面在那里把画面定调到**故意简单但已经定了**的程度：

| 在那里被定下的 | 具体是什么 |
|---|---|
| 放哪张图 | 这一屏用哪几张真实素材，各自什么身份 |
| 两张图是不是对比关系 | 并列 / 对比 / 因果 / 时序——写成语义事实，不写成画法 |
| 用什么样的模型展示 | 列表 / 流程 / 交叠 / 矩阵，或一个具体物件的示意图；一句话写在 `sample.note` |
| 模型上有什么字 | 必须原样出现的标签、数字、术语；写进 `exact_labels` 或 `sample.captions` |

粗糙可以，**没定不行**。这四件事是决定，随 `visual-plan.json` 被下游继承；**素材选择与这一层简单设计继承，版面不继承**。

## 两份内容，各司其职

- `visual-plan.json`：内容契约 + 上屏文字与花字声明 + 每屏样张。不塞布局参数和时间码。
- `production-brief.md`：记录表现提案、作者已选动作、参考资源、触发原句及开放项，以及**片级形状**。可以建议图形、分镜和运动逻辑，不把未审提案写成作者决定。

## 反模式

- 指定“左边放什么、右边放什么”作为表达设计（摆素材关系可以，写成分镜指令不行）；
- 提前选择流程图、卡片、三维模型等表现形式；
- 写淡入、滑入、缩放或逐帧动画；
- 录音前写出现秒数或 Visual Step；
- 把一句口播放大当画面需求；
- 为了让画面成立而补入资料中不存在的因果；
- 一屏跨越多个 Speech Beat，或一个 Beat 同时挂多屏；
- 声明一屏多状态，或把着重动画写成契约状态；
- 把样张做成设计稿：调字体、配色、动效，把内容审阅拖成审美评审；
- 用标注过的概念示意代替缺失的真实素材；
- 让某一屏在审阅页上什么都显示不出来还往下走。

## 与下游的关系

工作顺序是决定：**定故事与文案 → 做好静态画面 → 录人声 → 剪时间线 → 挂画面 → 按实测音频加轻动画 → 合成**。`visual-plan.json` 在**录制之前**就到做画面那一步。

- 做画面那一步：照声明的画，不判断声明。它仍自由决定风格方向、网格与层级、字号取值、色彩角色与跨页节奏；它不自由决定素材、关系、模型、模型上的字和花字。
- `video-craft`：读取内容契约、样张、最终口播、录音、SRT 和素材后，自主完成时间分组、动画状态、精确时间和实现审阅，并按本契约检查画面上的文字。样张的设计可以完全重做；用户对具体画面形式的反馈在下游审阅页处理，不回填成上游的构图指令。
